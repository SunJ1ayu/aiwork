## 0. 一句话结论

**隔离该做,并行不该做。** 但两件事的理由都不是 proposal 给的那个:

## 2. 更硬的一条:并行的上游供给是干的

派出一条腿的前置条件,是一份**已经攻过题、已经红检过、已经单独 commit 的 oracle**。
而 oracle 是铁律里"主 agent 亲写、绝不外包"的东西 ⇒ **oracle 只能串行产出**。

所以"同时存在两份可派的活"这个状态,在当前工作流里**一次都没出现过**——
而且这不是巧合,是被铁律在结构上排除的。要让它出现只有两条路:

- **(a) 主 agent 先连写两份 oracle 再一起派**:把主 agent 的串行段拉长一倍,
  去换执行段的并行。执行段 5 分钟,前置段 100 分钟 ⇒ **净收益为负**。
- **(b) 放松 oracle 铁律**:直接踩红线,不用讨论。

⇒ **Phase C(有界并行)不该进本单,也不该另开 track。** 这不是"以后再说",
是这条路的上游被堵死了;要重开,先得证明供给约束变了,而不是证明调度器写得好。

**这一条我认为是本次对抗最该拿去问 proposal 的地方**:它把"能不能并行"当成工具问题,
但它其实是工作流的形状问题。

**「补脚本和入口有效,补字段和约定无效」**。worktree 是约定 ⇒ 入口不做,它就消失了。

### 证据 3.2:此刻的现场就是混的

`design-studio` 主工作树里现在躺着执行腿 15:17 交的 8 个文件(未提交),

### 证据 3.3:闸① 的底账那段,主树一脏就失真

`delegate-codex:112-116` —— 底账用的是


**不限路径、也不减去派活那一刻已有的脏文件。** 主树本来就脏的话,

## 4. 我的方案:一个 flag,不是一个状态机

`delegate-codex --isolate`(倾向直接设为默认,`--no-isolate` 显式退出),只做四件:

1. `git worktree add /root/aiwork/worktrees/<job> <base>`;
   `<job>` 直接复用现有的 `NAME-TS` 命名(`delegate-<任务名>-<秒级时间戳>`),不另造 job id。
2. 回执里多存 `worktree` 和 `base` 两个键 —— 现成的 JSON 结构,加两个字段。
3. `--receive` 的四臂原样跑在 worktree 上;底账那句改成
   `git -C <worktree> status --porcelain -uall`,此时它**天然只含腿的改动**(证据 3.3 的洞自动关上)。
4. 收货通过后**打印**一条集成命令给主 agent 自己敲,**不自动 merge**。

### 明确不做,以及为什么

| 不做 | 理由 |
|---|---|
| job registry / manifest | 并发度是 1 时,状态就是"worktree 在不在",**磁盘本身就是账**。多一个 registry = 多一份会和磁盘对不上的第二账本。本机在"第二份账"上栽过:两个 track 都自称"第 3 单"。 |
| per-job lock / registry lock | 并发度 1 时锁没有对手 |
| 崩溃恢复状态机 | 崩了 worktree 就留在盘上,`git worktree list` 本身就是恢复入口 |
| **自动 cleanup** | **删的是唯一一份改动,不可逆。**改成收货通过后打印一行 `git worktree remove` 让我自己敲。mcp-registry 挂 8 天说明"忘"会发生 —— 但"忘"的代价是占盘,"自动删"的代价是丢活,**不对称**。 |

### 集成时必须查的两件(不是可选项)

- **`create mode 120000`**:worktree 里建的符号链接被 merge 带回主仓会**覆盖掉真目录**,
  本机出过事故;`.gitignore` 带尾斜杠只匹配目录,挡不住链接。
- **集成后重跑全量判据**,worktree 里的绿一律不许复用。
  (08-10 那单的教训:绿收据之后判卷面又改过、没重跑,是孤腿抓出来的。)

## 5. 真要缩 wall-clock,证据指向别处

按今天这单的分钟数从大到小排:

1. **主 agent 前置 100 分钟**。唯一看得见的可并行处是**攻题五轮是串行的**
   (14:56/14:58/15:01/15:04/15:12,一轮比一轮短,末轮 9 字节 = 没发现)。
   若这五轮之间我每轮都改了判据,那它**必须**串行(入口的"攻题记录不许旧过判卷"闸强制),
   这条就该砍;若不是,fan-out 三条不同视角的**只读**腿一轮拿三份就够了 ——
   现成工具是 panel 的扇出,**只读腿不写文件 ⇒ 根本没有归因问题,不需要 worktree**。
   **先测再说:那五轮里有几轮是"改完判据必须重攻"。**
2. **收货 + 四审 + 仲裁**(样本乙里跨了一夜)。四条评审腿早就并行,串行的是我读 diff。
   **隔离能把我要读的 diff 变干净 —— 这是隔离对 wall-clock 的唯一真实贡献,
   而且它落在验收段,不是执行段。**
3. **执行腿 5 分钟** —— 不值一个状态机。

## 6. 我这份方向可能错在哪(先自证伪,别等对方来打)

- **样本 n=2,且都是小活。** 大活(anydoc)执行段 22 分钟。但即便按 22 分钟算,
  两条并行也只省 22 分钟,前置仍是 100 分钟量级 —— 结论方向不变,幅度会变。
- **我可能答错了题。** 用户原话是"是不是**没办法**并行",问的是**能力**;
  我整篇在论证**收益**。有可能他要的就是"以后能并行"这个选项本身。
  ⇒ **这条必须问他,不能替他决定。**
- **隔离会新增一笔成本,而我没有数据**:今天 15:19 主 agent 就是在同一棵树上改判据的。
  隔离之后"我改判据"和"腿改实现"分居两棵树,合并时会多一步。
  这一单占比多大,不知道 —— **真开放问题,不假装已经算清。**
- **我对 Phase C 的否决建立在"oracle 必须主 agent 亲写"这条铁律上。**
  铁律若变,结论跟着变。但铁律不该为了并行而变,这是尾巴摇狗。
