# Proposal: redcheck-pycache

- Date: 2026-08-08

## 问题(一句话)

`redcheck`(退回红检)换完代码不清 Python 字节码缓存 ⇒ **它跑的可能是上一版的代码**,
于是"这份判据到底证明了什么"这个唯一的机械答案,本身会撒谎。

## 触发它的实事故(2026-08-07 深夜,anydoc 三轮收口)

我手搓了一次性红检脚本(**没用 `redcheck`,这是另一笔账**),把
`fence_end = f"【资料结束 #{nonce}】"` 改成 `fence_end = "【资料结束 #deadbeef】"`
去验证那条判据会不会红。**两串恰好都是 17 个字符**,加上 `cp` 还原时 mtime 落在同一秒 ——
CPython 的 `.pyc` 有效性检查(源文件 mtime + size)整个通过,解释器用的是旧字节码:

1. 先**假绿**:红检报告"这是条死判据"(其实跑的是没被改坏的代码);
2. 还原之后又**假红**:干净的树上那条判据失败(跑的是被改坏的旧字节码),
   我一度以为自己刚提交的改动把它弄坏了。

## 为什么值得单独修(而不是"下次记得清缓存")

红检是**判据到底证明了什么**的唯一机械答案。它自己会撒谎的话,上面那一整套
(判据先行 / 退回红检 / 死断言闸)全落在流沙上。而且这种谎最容易发生在
**同长度的最小改动**上 —— 也就是最典型的红检手法。

`redcheck` 走的是同一条路:`git checkout <base> -- <impl>` 写出来的 mtime 同样是"现在",
同长度回退照样撞得上。**它至今没撞上只是运气。**

## 不做什么

- 不加新的闸、不动任何触发条件。这一单是**修一个已知会撒谎的工具**,不是加规矩。
- 不去清 `node_modules`、不清 build 产物 —— build 那半截已经有 `--build` 管着。
