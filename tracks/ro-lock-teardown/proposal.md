# Proposal: ro-lock-teardown

- Date: 2026-08-19
- Status: open

## Goal

拆掉评审腿的**只读锁**(`bin/ro-repo-exec` 那套 mount namespace 挂载),改用两件更轻的东西:
① 腿的产出目录一律钉在**仓外**(卫生,已对 kimi 做过,本单补 mimo 的 plan 目录);
② 需要隔离时用**独立工作树**(派活侧已有的成熟机制),而不是把仓库焊死。

## Motivation

同一天上午刚建起来的这套锁(track `repo-write-audit`,已归档 `f8f8c61`),当晚被业主
两次质疑推翻。**推翻它的是证据,不是偏好**:

1. **它防的那件事不是威胁,是腿正常干活的方式。** 唯一一次"评审腿写仓"的实证是
   `logs/panel-worktree-sweep-review-20260811-235830.submimo.log:695` —— submimo 在
   `mode: review` 下写了 `.mimocode/plans/…hidden-circuit.md`,内容是**它自己的评审报告**
   (`# Review Report / Verdict: PASS with findings`)。而这类文件**历史上是当工件入库的**
   (commit `ef5272a` 原话:「同目录另外 7 份**本来就入库,按惯例**」)。
   全部评审腿日志里,写到自己 plan 目录之外的记录:**0 次**;碰代码或判据:**0 次**。
2. **锁与"腿要有执行能力"直接冲突。** 业主明确要让其他腿也具备执行能力。锁的作用就是
   禁止写,腿越强、想动手核实的场合越多,锁挡掉的越是正经工作。08-19 当天已预演一次:
   subdeepseek 想跑一遍判据核实自己的发现,被拦住 —— 它不是捣乱,是在干正事。
3. **它挡不住真正造成过损害的那件事。** `panel-dsbash-0819b.subdeepseek.stream.jsonl`:
   permission_denied **0 次**、`timeout 300 bash tests/test-review-tooling.sh` 真执行 1 次、
   `duration_ms=547296` 后 error_during_execution,留下遗孤吃内存。那是**命令白名单**的活,
   只读锁的射程根本不覆盖(跑判据是"执行",不是"仓内写")。

## 真问题(第一性)

- **用户原话**(原封不动):
  - (今早)「底座加模型够聪明是不是不需要加那么多限制」—— 我当时答「其他腿没做测试,
    没理由去改试卷」,**然后我还是做了这套锁**。
  - 「但是我们不是讨论过没必要给评审腿上锁吗 他们也不会动试卷啊」
  - 「他写入应该算正常的」
  - 「其他腿也要有执行能力 可能以后会把mimo换成其他的」
- **真正要解决的是**:腿的能力要**加**,而锁是在**减**。真实需求是"腿动手时别把主仓弄脏",
  不是"腿一个字都不许写"。前者用落点管理(产出钉仓外)+ 隔离树就够;后者才需要焊死仓库。
- **我在这中间翻译错了什么**(记下来,因为它当场被纠正):
  我把「可能以后会把 mimo 换成其他的」翻译成**"要换底座"**,还拿"换底座的适配成本"
  当了一条论据。业主当场纠正:「不用换底座啊 你在说什么其他腿都好好的」。
  ⇒ 他说的是**执行腿这个角色可能换人**,不是把 mimo 这个底座换掉。**那条论据作废**
  (结论不依赖它)。

## Scope

- in: 摘掉三个包装器(`submimo` / `subkimi` / `subagent`)里对 `ro-repo-exec` 的调用
- in: 删除 `bin/ro-repo-exec` 及**仅**为它存在的判据
- in: 把 mimo 的 plan 产出目录钉到**仓外**(与 kimi 运行期 home 同一手法)
- in: 判据先行 —— 先有能咬住"腿的产出不落进仓"的断言,再拆

## Non-goals

- **不动**已做的卫生改进:kimi 运行期 home 在仓外(V38)、腿 argv 写口为零(V37)
- **不动** V41(判据不许把注释交给 shell 执行)—— 它与锁无关,是判据自己的病
- **不做**给其他腿加执行能力(那是另一单)
- **不做**工作树隔离的改造 —— 派活侧(`delegate-codex`)已有,本单只是不再用锁顶替它
- **不碰**命令白名单/守卫 —— 那才是"腿跑判据吃内存"的正解,但属另一单

## 已知风险(GPT 对抗评审提出,成立)

- **按数字批量删判据会误删该留的**:锁前 367 条 → 现在 430 条,差值 63 里混着 V38(卫生)、
  V41(与锁无关)。⇒ 必须**逐条判断**,不许按区间删。
- **`unshare` 依赖不会因拆锁而消失**:`tests/lib/_no-egress.sh:47` 本来就要 `unshare -n`。
  ⇒ 本单不许把"拆锁 = 判据能跨环境跑"写进任何结论。
