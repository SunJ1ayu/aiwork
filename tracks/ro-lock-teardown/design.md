## 现状:防线其实有三层,不是一层

拆之前必须先看清楚拆的是哪一层。**这是本单最重要的事实,它推翻了我最初的方案**:

| 层 | 位置 | 挡什么 | 加的时间 |
|---|---|---|---|
| ① 工具级 deny | `bin/submimo:170-183` 生成的 `mimocode.json`;claude 壳的 `--disallowedTools`;kimi 的 `guard.mjs` | `write`/`edit`/`patch`/`task` 等工具**整个关掉** | **08-19 今天** |
| ② bash 白名单 | 同上三处,各自实现 | 只放行只读 git 子命令 | 08-18~19 |
| ③ 只读挂载锁 | `bin/ro-repo-exec` + 三个包装器 | 内核级:仓内**任何**写 | **08-19 今天** |

**08-11 那次 submimo 写 plan 文件,是因为①②③当时都不存在。** 用它来论证"必须有③"
是错的时间线 —— ① 单独就足以挡住工具级写。

### 那 ③ 的真实价值是什么(唯一一条,但它是真的)

**兜住 ② 的已知洞。** 三条腿的白名单都是前缀通配:
- mimo:`"git diff*": "allow"`
- claude 壳(deepseek/glm):`--allowedTools Bash(git diff:*)`
- kimi:`guard.mjs` 的 `^git\s+` 锚定

`git diff --output=<仓内路径>` **全部命中放行**,而它会写文件。这个洞 08-18 亲手复现过
(见记忆 `opencode-agent-base-track`)。只读锁是目前唯一挡住它的东西。

## Approach

**先堵洞,再拆锁。顺序不能反** —— 反了中间就有一段防线净变弱的窗口。

1. **S1 堵 ②**:三条腿的 git 白名单从"前缀通配"收紧到"不许带写出参数"。
   最小充分集:禁 `--output`(含 `--output=x` 与 `--output x` 两种写法)。
   > 不做全黑名单枚举 —— 那是漏一个就白做的思路。做法是**只放行不带 `-` 前缀参数的
   > 只读子命令**,或显式拒绝 `--output`;具体形态在 tasks 里逐腿定,判据先咬住行为。
2. **S2 钉产出落点**:mimo 的 plan 目录钉到仓外。
   `mimo debug paths` 显示 data 默认已是 `/root/.local/share/mimocode`(仓外),
   但它有"项目本地"分支会落到 `<cwd>/.mimocode/`。要么显式配置,要么让腿的 cwd 不在仓内。
   与 kimi 运行期 home(V38)同一手法。
3. **S3 拆 ③**:摘掉三个包装器里的 `RO_EXEC`(`subkimi:148-149,226` / `submimo:133-135,257` /
   `subagent:290-291,357,385`),删 `bin/ro-repo-exec`。
4. **S4 收判据**:**逐条**判断,不许按区间删(锁前 367 → 现在 430,差值 63 里混着必须留的)。
   留:V37(argv 写口为零)、V38(运行期 home 在仓外)、V41(判据不许把注释交给 shell)。
   删:仅在"仓被挂成只读"这个前提下才成立的断言(V35 主体、V36 的 BLOCKED 断言、V39、
   V40④⑤、V42 全部)。**每删一条都要在 tasks 里写明它依赖的前提已不存在。**

## 测试策略(oracle —— 主 agent 所有,不外包)

判据必须能回答四个问题,**其中第一个是拆锁的前置条件**:

- **O1(前置)**:三条腿的白名单**不许**放行 `git diff --output=…`。
  先红:当前配置下这条必红(洞还在),堵完转绿。**这条不绿,不许动 S3。**
- **O2**:摘掉锁之后,腿的**工具级写口仍然为零**(V37 继续咬,不许跟着锁一起被删)。
- **O3**:腿的产出不落进仓 —— 跑一轮 review 之后 `git status --porcelain --ignored`
  在仓内不出现 `.mimocode/`。
  > 注意用 `--ignored`:`.mimocode` 在 `.gitignore:46`,不带这个参数**看不见**——
  > 这正是我最初那个"事后 git status"方案对真实案例是瞎的原因,写进判据别再犯。
- **O4(防误删)**:V37/V38/V41 在拆完之后**仍然存在且仍然绿**。
  用一条元断言钉住:这三段的函数名必须还在调用列表里。

**红检要求**:O1 必须在堵洞前红过;O4 要做变异 —— 故意删掉 V38 的调用,元断言必须变红,
证明它不是"永远绿"。

## Key trade-offs / risks

- **净防护力是下降的,要认**:③ 走了之后,`git diff --output=` 只剩 ② 挡(软防线,依赖
  底座尊重配置),不再有内核兜底。换来的是腿能动手、少 190 行 + 一批判据、不再有
  `CAP_SYS_ADMIN`/git 版本这类环境耦合。**这是业主拍板的取舍,不是我判定"没风险"。**
- **威胁模型不变**:仍是"误伤 + 提示注入",不含有动机的对手。有动机的对手在 namespace
  里本来就能自己 remount,③ 也挡不住 —— 这条在 `repo-write-audit` 的 design 里就写着。
- **不许写进结论的一句**:"拆锁 = 判据能跨环境跑"。`unshare` 依赖来自 `tests/lib/_no-egress.sh:47`,
  与锁无关,拆了也还在。
- **回退成本**:`ro-repo-exec` 删掉后要恢复,靠 git 历史(`f8f8c61` 之前的树)。不做兼容层。
