# Design: design-before-build

## 主 agent 的初始方向(读外部意见之前)

先改解释工作流的协议,不造一个不会判断内容的新闸。现有错误来自指导 agent 判断的入口写得过窄:
「有多个架构方向才花独立思考」没有覆盖「只有一个方向,但没有验证它是否满足用户目标」。

拟把 panel 的设计段作为唯一详细规则,其它入口链接过去。所有非平凡方案先用事实描述目标、
方案改变的行为、成败依赖和选错后的代价。关键未知先做探针;关键取舍/高返工代价触发一个
不同家族的独立方案挑战,有真实方向分叉才扩大到多家族 panel-explore。
确定且局部可逆的修改直接做,不要求双出。Jev 只提醒/排序;不能因其低分取消独立检查。

主 agent 的方向记录不喂给独立模型;外部意见作为待核实证据。低分/一致意见都不是免验凭据。
沿用 decision.design.premise_attack 的 done/evidence 表示实际发生的检查,不增加自报字段。

## 尚未验证的取舍

- 文档协议是否仍太容易被绕过?机器只能查工件存在,不能判断独立性/前提合理性;需要实例走读与后续真实任务观察。
- 「高返工代价」是否过于含糊,会让所有 high 风险任务默认全池?应按具体可观察的变更约束定义,与 impact 分开。
- 最小独立检查能否利用现有 explore 单腿入口,避免 panel-explore 默认全池的成本和坏腿问题?
- 是否必须修改 delegate/模板旧双出条件才能消除入口矛盾?需要逐条追踪。

## Test strategy

不为散文写关键词测试。主 agent 走读反例:明确要求下的启动阻塞、数据迁移、纯局部文案、
已测清的窄修复、有目标冲突的外部依赖;要求路线能区分,并不凭已知答案调整阈值。
跑现有 workflow-docs 部署检查及 track-record/track-preflight 兼容性检查;独立评审查入口矛盾。
这些只证明协议一致、旧契约未破坏,不证明行为或返工率改善。
