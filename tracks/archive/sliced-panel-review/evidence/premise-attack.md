## 1. 独立对抗评审(sub codex)最终报告

**我的反方结论：可以试验“切片是否提高检出”，但现在不该把“切片覆盖齐全”升级成替代两腿整任务审查的放行依据。** 最危险的新增部分是覆盖契约和裁决语义，不是派发器。

我只读检查了代码，提出以下 5 点。

1. **[BLOCK：作为等价替代时] 切片把共同盲点前移到了切片器，一条跨片腿无法自动补回独立性。**

   思想实验：把“派发与恢复”“结果落盘”“花名册”分给三片。每片都能证明自己的常规路径正确；但控制器在第一条腿完成前死亡，退出码无人持久化。问题不是某个接口参数不匹配，而是三个模块在同一故障时序下共同失效。

   这就是代码记载过的真实问题：[`panel-review:650`](/root/aiwork/bin/panel-review:650) 明确解释为什么“控制器增量落盘”仍然会丢全部结果。把每个文件、调用方、测试分配齐全，不能证明这种时序有人独立推演过。

   跨片腿如果沿同一计划检查列出的接口，也会继承切片器的盲点；如果从原始需求重新推演全局失效模式，它承担的是一轮实质性整体审查。必须承认这部分成本，不能把它设计成廉价扫查后宣称强度保持不变。

2. **[BLOCK：接入现行归档时] 现有 subject 绑定的是任务原文，切片任务不是能直接塞进去的新字段。**

   [`_review_result.py:193`](/root/aiwork/bin/_review_result.py:193) 将 `task_sha256`、源码和 delivery 一起构成 subject；[`track-record:1096`](/root/aiwork/bin/track-record:1096) 只承认同一次 run、同一个 subject 的家族覆盖。

   两条最直接的实现路线都有问题：

   - 每片生成自己的 task：任务摘要不同，subject 分裂，两个家族不能组成当前合格组。
   - 保留统一 task，但通过额外提示限制各腿责任：旧 eligibility 只检查完整 snapshot、完整证据、身份等事实，两个局部 PASS 仍可能被错误计成整体双家族覆盖。见 [`_review_result.py:585`](/root/aiwork/bin/_review_result.py:585)。

   因此应区分“被审交付物身份”和“审查任务身份”，并明确版本迁移与 reader 行为。**未改放行门槛的试点，也必须确保局部结果不会混入旧 coverage。**

3. **[BLOCK：自动裁决前] “不同 scope 的 PASS/BLOCK 不算冲突”不等于可以放行，需要独立的未解决问题账。**

   反例：甲片发现其调用方在乙片违反协议，报告 BLOCK；乙片自审 PASS；跨片腿 PASS。这个 BLOCK 应该挂在哪个 scope？如果甲片发现被判“超范围”，或者乙片 PASS 被当成已经否定它，真实问题就消失了。

   当前 [`_review_result.py:631`](/root/aiwork/bin/_review_result.py:631) 的冲突判定虽然粗，但会保留 PASS/BLOCK 的不一致。切片确实需要改变它，但不能只做“按 scope 分组”。

   至少需要明确：范围外发现仍然有效；哪个证据否定或解决了哪个 finding；复核不能覆盖原报告；重试不能靠取最后一个 PASS 消除旧 BLOCK。仅登记 `scope/role/attempt` 不能回答这些问题。**“只复核重要 findings”还需要防止主 agent 通过调低重要性，让反对意见绕过复核。**

4. **[实验取舍] 目前缺少值得承担这套复杂度的成本证据，默认 high 的对手是两腿。**

   [`panel-review:30`](/root/aiwork/bin/panel-review:30) 默认启动两个家族；[`panel-review:785`](/root/aiwork/bin/panel-review:785) 只在证据问题等情况下补一条腿。你补充的最近 20 轮基线也支持这一点。

   两片各双家族深审，再加一条跨片腿，至少是 5 个任务，后面还有定点复核。各片包含实现、调用方和测试，会重复加载共享上下文；复核又增加串行尾部。它可能提高质量，但不能先假设更省钱、更快。

   需要测的是**同等总预算下的有效缺陷检出**，而非每条腿平均输入变短。现有 usage 缺少成本和 token 数据，先解决测量问题更划算。

5. **[实验取舍] 一个新编排模块仍可能带来第二套生命周期系统。**

   现有 [`panel-review:660`](/root/aiwork/bin/panel-review:660) 把终态写入放在独立会话内；[`panel-review:753`](/root/aiwork/bin/panel-review:753) 在派发前落盘计划，都是事故后建立的恢复保证。

   “同腿多个任务、动态扩大范围、补派、后置复核”意味着任务图会变化：计划变更后旧结果是否有效？控制器死在发现问题与创建复核任务之间如何恢复？补派完成时如何避免覆盖原尝试？这些不能仅靠新增 `attempt` 字段解决。

   第一版应把任务图固定下来，限制动态扩片与自动复核，不然为验证一个审查质量假设，会先重造一套调度状态机。

**我更支持的最小替代方案：先保留两条整任务腿，试“不同审查重点”，再试真正的局部责任。**

两腿仍对整个任务负责，共享同一份冻结任务，分别强调不同失效类型；先验证聚焦提示是否改善结果，不改 coverage。如果要直接试切片，就在隔离的离线实验里固定 2～3 片，加一条从原始需求独立开展的整体审查；结果只做评估，不贡献现行归档资格，也先不做动态任务图。

会改变我判断的证据是：在不向模型透露答案的缺陷快照上，与当前两腿进行同预算对照；包含局部缺陷，也包含控制器死亡、跨模块状态、配置与兼容性等跨片缺陷；切片方案在严重问题检出上没有明显退步，并确实降低成本或耗时。还要换一种合理切法重复比较——**如果检出高度依赖主 agent 恰好切对，架构只是把能力瓶颈搬到了切片器。**

### GPT 2026-09-13T12:30:31.587Z

**可以借鉴。我建议做成“按职责切片深审 + 独立跨片审查 + 问题定点复核”，由 aiwork 统一编排。** 不同模型腿负责不同任务，主 agent 最后基于证据裁决。

查到的 Grok Build 官方流程确实是：收集上下文 → 专项审查并行 → 对发现的问题做对抗验证 → 汇总。它支持这个方向，但公开说明没有把切片固定成按文件或行数切分。[官方说明](https://x.ai/news/workflows)

结合当前 aiwork，我会这样设计。

**1. 按“行为链路”切片，每片包含实现、调用方和测试。**

比如审查 aiwork 自己，可以这样分：

| 切片 | 主要责任 |
|---|---|
| 派发与恢复 | 选腿、预算、重试、超时、降级 |
| 审查结果 | 身份、证据完整性、结论解析 |
| 交付与归档 | snapshot、delivery digest、覆盖资格、归档检查 |

每片拿到公共的任务目标、完整变更清单，再附自己的重点代码、依赖和测试。**切片限定审查责任，保留读取完整仓库的能力**；发现依赖超出范围，可以请求补充或扩大范围。

切片方案本身也要检查：有没有变更无人负责？两个切片之间的数据契约由谁审？否则切片器一次漏分，后面所有腿都会漏看。

**2. 把“交叉验证”拆成两种工作。**

```text
固定本轮源码快照与审查计划
             │
       ┌─────┴──────────┐
       │                │
  多腿分片深审     独立跨片审查
       │          检查切分遗漏、
       │          接口与整体行为
       └─────┬──────────┘
             │
   换模型家族定点复核 findings
             │
      主 agent 裁决与覆盖检查
```

这里最关键的是：

- **跨片审查补漏。** 独立读取原始变更，检查调用链、共享状态、失败恢复、整体目标是否满足。开始时不看其他腿的结论，避免被带偏。
- **定点复核降误报。** 拿到某个 finding 后，尝试反驳它、复现它，确认是不是本次变更引入的问题。

只复核 findings 不够：所有切片都漏掉的问题，根本不会进入复核队列。

**3. 把“审查任务”与“模型腿”分开。**

现在 [`panel-review`](/root/aiwork/bin/panel-review:714) 主要按腿启动和记录结果。切片后，应该由计划描述“要审什么”，健康池决定“交给谁”：

- 一个切片可以交给不同模型家族复审。
- 同一条腿可以先后承担多个切片，每次使用独立上下文。
- 某条腿失败，补派它承担的任务。
- 日志和结果按任务、尝试次数记录，避免同一腿多次运行互相覆盖。

第一版继续复用现有腿适配器、健康池和隔离机制；**新增一个集中管理切片、派发关系和覆盖判定的编排模块**，无需一开始就做通用多层 agent 平台。

也先别固定“某模型永远审某领域”。先轮换并积累效果数据，再决定是否值得按能力分配。

**4. aiwork 最需要改的是覆盖语义。**

当前 [`_review_result.py`](/root/aiwork/bin/_review_result.py:631) 按同一次运行、同一 subject 下的合格模型家族数汇总。切片后：

> A 腿审切片甲，B 腿审切片乙，只能证明两个切片分别有人审过，不能证明任何一个切片获得双重审查。

因此结果需要明确绑定：

- 本轮源码与交付快照；
- 审查计划版本；
- 切片及责任范围；
- 审查角色：深审、跨片、问题复核；
- 完成状态、证据及模型家族。

最终检查应该回答“每个必审范围是否满足要求”。**收到完整 snapshot 只是具备完整视野，不能自动算作全量审查完成。** 切片之间出现 PASS/BLOCK，也不能直接沿用现在的全局冲突判断，要看是不是对同一问题或范围持不同结论。

**5. 保底强度要明确，避免在切片时悄悄降档。**

我建议的目标策略是：

| 场景 | 建议策略 |
|---|---|
| 小改动、强耦合改动 | 延续现有整任务审查，省去切片开销 |
| 较大且可分的改动 | 每片深审 + 一次独立跨片审查 + 重要问题换家族复核 |
| 高风险范围 | 每个高风险切片由两个不同家族深审，再做跨片检查 |
| 分片困难、缺上下文或覆盖不足 | 扩大范围或回到整任务审查 |

**一条全局扫查腿，不能默认抵扣每片的第二次深审。** 如果它确实完整审了某片，可以明确记录那部分覆盖；只检查接口，就只记接口覆盖。

成本上也要诚实：当前默认 high 已经是两腿整任务审查，切成“两片 + 一条全局腿”未必更便宜。收益更可能来自聚焦后的审查深度，以及相对多腿全量审查减少重复阅读，需要实测。

**我会先做一个范围很小的试点：手工切 2～3 片，计划落盘，复用现有腿，新增覆盖矩阵，在历史变更上与原流程对照。** 看已知缺陷检出、跨片漏报、误报、总成本和耗时。试点期间保留现有归档要求；有证据后再调整正式覆盖契约。自动切片和修复后局部重审放到后面，因为这两件事最容易把依赖遗漏藏起来。
