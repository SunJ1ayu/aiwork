# Proposal: codex-worktree-delegation

- Date: 2026-08-11
- Status: open
- 文档身份: **Codex 独立方向草案,不是最终裁决**。后续由 Claude Code 先对抗、再综合。

## Goal

把 Codex 执行腿从“直接写当前工作树的一次性前台调用”升级为：

1. **单任务默认隔离**：每一单都有独立 worktree、基线、job id、日志和回执；
2. **先把串行做可靠**：即使只跑一条腿，也能明确归因、失败回收、跨会话恢复；
3. **再做有界并行**：只对依赖独立、声明写集不相交的任务开放，初始并发上限 2；
4. **主 agent 的判断权不下放**：执行腿仍不 merge、不 push、不归档、不下最终裁决；
5. **集成后重新判卷**：各腿单独通过不等于组合后通过。

## Motivation

当前 `/root/aiwork/bin/delegate-codex` 已经把派活三件套、attack-log、protect 清单和
收货闸①机械化，但它的工件模型仍是“一条腿独占一个工作树”：

- 单次命令前台阻塞，没有 batch/fan-out/队列；
- 没有全局锁，也没有 per-job worktree；Codex CLI 进程可以被外部同时拉起，
  但当前工具没有为这种并发提供归因和集成语义；
- 回执记录的是 `repo + 派活时 HEAD + protect`，`--receive` 查看的是该工作树从基线以来的
  **全部**改动；两条腿共写同一工作树时，两份回执都会看到混合 diff，无法证明谁写了什么；
- 一条腿可能在运行中读到另一条腿尚未完成的文件；即使文件表面不冲突，也会形成不稳定输入；
- 默认日志名只有“任务名 + 秒级时间戳”，同名任务同秒启动存在碰撞窗口；
- 当前失败后留下的是一个混合工作树，不能可靠地单独保留、重跑或丢弃某条腿；
- 主 agent 的闸②、闸③和最终集成仍是串行判断。盲目增加腿数可能只把等待队列从“实现”
  搬到“验收”，所以并行收益必须用真实耗时账证明。

这说明真正缺的不是一个 `&`，而是**隔离、身份、生命周期和集成协议**。

## 真问题(第一性)

- 用户原话:
  - 「我刚刚看到我们aiwork的工作流codex作为执行腿是不是没办法并行」
  - 「那你觉得这一步是升级工作流的必要路径还是还有别的方向呢」
  - 「后续我需要让claude code来对抗最后合并方案」
- 真正要解决的是:让可拆分任务在不稀释 oracle、三道闸和主 agent 仲裁权的前提下，
  安全缩短 wall-clock；即使最后证明“不值得并行”，单腿也应先获得干净归因和可恢复性。
- 我在这中间翻译了什么:没有把需求翻译成“多开几个 Codex”，而是翻译成
  **串行也默认隔离 → 工件可归因 → 量出瓶颈 → 满足条件才开放并行**。
  这份翻译可能错：如果真实瓶颈长期在主 agent 写 oracle/读 diff，而不是执行等待，
  并行层的收益会很小；后续 Claude Code 必须专门攻击这一前提。

## Claude Code 接手协议

这是新写面/开放方向。后续 Claude Code 接手时不要直接把本 design 润色成“共识”：

1. 先只读本 proposal、当前 `delegate-codex` 源码、`delegate` skill 和 track 约定；
2. **暂不读 design.md 的技术方案**，先把自己的独立方向落到
   `/root/aiwork/logs/codex-worktree-delegation-claude-independent.md`；
3. 再读 design.md，逐条攻击其中的不变量、状态机、目录选择、失败恢复和并行收益假设；
4. 把“采纳 / 驳回 / 改写”及依据写回 design.md 的“Claude Code 对抗与合并”章节；
5. 与用户收敛后才把 `Status: draft` 改成选定方案。不得把本文件当作已经拍板的规格。

这样做的目的不是制造两份文档，而是保留一轮真正独立的方向，再把结果合并回唯一 design。

## Scope

- in:
  - 独立 worktree 的创建、登记、运行、收货、保留、集成和安全清理；
  - 唯一 job id 和 job manifest；
  - 显式基线、protect 清单、预期写范围、日志/receipt 归属；
  - 崩溃后从磁盘恢复状态；
  - 两任务有界并行的资格检查和调度；
  - 主 agent 串行集成、冲突停止、集成后完整判卷；
  - 假 Codex + 临时 git 仓的回归 oracle；
  - 对现有 `delegate-codex` 的兼容与文档更新。

## Non-goals

- 不允许两条执行腿并行写同一个物理工作树。
- 不把 fork/后台分身重新包装成“执行档”；每条腿仍是窄任务书 + 独立交货。
- 不让任何执行腿自动 merge、push、归档、改 oracle、装依赖或扩大网络权限。
- 不用并行替代 attack-log、红检、三道收货闸或 full/fast/self lane。
- 不在第一版做任意 DAG 调度、跨机器执行、自动冲突解决或无限并发。
- 不承诺“文件不相交就一定语义独立”；共享协议、生成物、数据库、端口和缓存也算依赖。
- 本 track 当前只沉淀方向，不在没有 Claude Code 对抗和用户收敛前直接实现。

## Success criteria

- 串行单任务也默认在独立 worktree 运行，主工作树在 `integrate` 之前逐字节不被执行腿触碰；
- 每个任务可由 job id 唯一定位其基线、worktree、任务书、attack-log hash、protect、日志和回执；
- 两个并行任务的改动、失败和清理能独立处理，不存在混合 diff；
- 声明范围冲突在派发前拒绝，实际范围漂移在收货时显式 BLOCK/待主 agent 仲裁；
- 任一腿失败、超时或进程崩溃时保留现场，不自动删除唯一改动；
- 主 agent 只能串行集成候选，冲突时停止；集成后必须重新跑 oracle + 回归 + build；
- 通过真实样本证明并行减少总 wall-clock，且没有提高返工、错归因或集成失败率；
- 如果测量表明验收才是瓶颈，允许以“只保留串行隔离、不上线并行”作为成功结论。
