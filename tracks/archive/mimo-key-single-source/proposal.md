# proposal: mimo key 只许有一个源头

## 起因

2026-09-01 业主的小米 mimo 账号过期,换 key。换的过程本身暴露了真问题:

**那把 key 抄在 9 处,没有任何唯一源头。** 我第一轮手工替换时**漏掉 3 处**,
报给业主「5 个位置全换好了」——是业主一句「submimo 腿一起改」才逼出扫全 `/root`,
又挖出 3 个活位置。其中最阴的一处:

- `/root/.local/share/mimocode/auth.json` 是 submimo 的 **canonical home**,
  `submimo-iso` 每次跑都从它 re-seed 凭证到隔离树。只改隔离树那两份的话,
  **下一次派活就把旧 key 播回去了**,而且不报错、只 401。

业主随后问「是遵循的第一性原理吗,没有留下屎山吧」。诚实回答是**没有**:
我做的是「把 9 份挨个改一遍」,治的是症状;留下的防漏措施是**记忆里一张手抄清单**,
而手抄清单会腐烂——这正是本仓反复批评的形状(规矩4 名单手列 ⇒ 新增一处就漏,
漏的时候没人知道)。

## 查现状时挖出的活 bug(改变了方案)

`GitHub-Watch-每日监控` 那条 cron 的**提示词里内嵌了 `export LLM_API_KEY=***`**
——字面三个星号,不是真 key。而 `watch.py` 的取值顺序是:

```python
api_key = os.environ.get("LLM_API_KEY", "")          # 环境变量优先
...
if not api_key and config_file.exists():             # 空了才读配置文件
```

`***` 非空 ⇒ **配置文件那条回落路径整条被挡死** ⇒ 每次调 AI 都拿 `***` 去认证 ⇒ 401
⇒ 而调用处 `except Exception: return ""` **静默回退**,任务照报 `status: ok`。

**实测(不是推的):**分别在 `LLM_API_KEY=***` 与不设该变量两种环境下 import 一次
`watch.py`,读它算出来的 `LLM_API_KEY`:

| 环境 | 它实际用的 key |
|---|---|
| 提示词那样设 `LLM_API_KEY=***` | `'***'` |
| 不设该变量 | `tp-c8b…`(配置文件里那把真的) |

**旁证:**那条任务的提示词自己写着「如果 release notes 没被翻译,用你自己的能力翻译」
—— 业主早发现日报夹英文,当时是让 agent 事后补救,没找到根子。

这条把方案从「写个工具把 9 处一起改」改成了**「有两处根本该删掉,删了反而更对」**。

## 目标

1. **能删的删掉**(最彻底的去重是不存在)
2. **不能删的,由一个工具写**,人不再手动碰
3. **「还有没有别处藏着 key」由机器扫,不靠我的记性**

## 不做

- 不动 `rust-check-review-tooling` 的超时自报(业主明确说「防锈工具先不动」),
  该项另记 backlog
- 不验 key 的有效性于判卷面(判卷面不许有外网出口),有效性由 rotate 工具在换的当下验
- 不清理历史备份/日志里的旧 key(那些是死 key,且是历史证据)
