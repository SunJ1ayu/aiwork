# Design: panel-roster-from-disk

- Change: panel-roster-from-disk
- Status: 方向已定,判据先行
- base-ref: 0d68e7a

- 规划双出: 不做。这不是开放架构分叉 —— 根因是一条可验证的机械事实(见下),
  方向由它唯一确定。真正值得写下来的是**那个看起来对、其实修不好的选项**,
  它在下面「② 增量写」里,连同证伪它的那条时间线。

## 根因(读代码读出来的,不是推的)

`bin/panel-review:541`:

```bash
wait_leg() { local name="$1" rc; wait "${LEG_PID[$name]}"; rc=$?; LEG_RC[$name]="$rc"; }
```

**每条腿的退出码是 `wait` 拿到的,而 `wait` 只有亲手启动那条腿的那个进程能用。**
于是它只活在控制器的内存里,全程一次也没写进磁盘。

整套系统里,花名册需要的事实只有这一件不落盘,而其余部分**全部**由它推导:

| 现象 | 为什么 |
|---|---|
| 只有控制器能写花名册 | 只有它知道 rc |
| 花名册只能最后一次性写(`:730`) | rc 要等腿跑完才有 |
| 控制器一死 ⇒ 零记录 | rc **永久消失**,不是"没来得及写"是"再也算不出来" |

⇒ **修的不是"谁来写花名册",是"退出码该由谁落盘"。**

## 方案(选中):事实由「最早知道它、且活得最久」的那一方落盘

拆成三件,各自独立:

1. **`<prefix>.plan`** —— 派谁、预算多少、health 状态、`HEAD_BEFORE`、task 名。
   这些在**派发之前**就全部已知(`:338`~`:399` 选腿逻辑跑在 `launch_leg` 之前)。
   ⇒ 控制器**在派发前**立刻落盘。不依赖它活到最后。
2. **`<prefix>.<leg>.state`** —— 那条腿的退出码 + 起止时间。
   **由腿自己那条 session 里的包装器写**,不是控制器写。
3. **花名册 = f(plan, state\*)** —— 纯函数,读盘算出来。控制器正常收尾时调它;
   **`panel-roster <prefix>` 单独入口**让任何人任何时候事后重建。

## 被否决的三个,以及为什么(这一节是本设计的重点)

### ① 给控制器焊 `setsid`
只挡 SIGTERM。挡不住 SIGKILL、OOM、断电、机器重启。
**它保护的是"那个会死的进程";而我要的是"记录不依赖任何进程活着"。**

### ② 控制器**增量**写花名册(⚠️ 看起来对,实际修不好今天这次)
"别最后一次性写,每条腿跑完就更新一次" —— 听上去正是治本。**但它写在哪儿?
还是 `wait_leg` 返回之后**,而 `wait_leg` 在控制器里。

用 08-23 那次的真实时间线证伪它:

```
11:49:09  控制器派出 subglm(腿进新 session,活)
11:51:07  控制器被 timeout 120 杀   ← 此刻还没有任何一条腿跑完
~11:59    腿本来会跑完(参照 r3 实测 584 秒)
```

**控制器死在第一条腿交卷之前**,增量写和一次性写落盘的字节数完全相同:0。
⇒ 记录必须由**腿自己**写,这就是方案第 2 条要把包装器塞进 setsid 里面的原因。

### ③ `trap` SIGTERM,被杀时抢救一把
同 ②:被杀那一刻 rc 还不存在,抢救不出任何东西。而且 `trap` 对 SIGKILL 无效。
`panel-review` 全文 794 行**一个 trap 都没有**,本单也不加。
> 注:`subkimi` 里那套"先写裁决、超时也不亏"的兜底,`:517` 的注释已经写明
> **防不了这个** —— 被 SIGTERM 打死时抢救代码根本没机会跑。同一个坑别再踩。

## 前提已验(不是推的):腿活得比控制器久

设计整个压在「腿被 setsid 焊住、活得比控制器久,而退出码只活在控制器内存里」上。
当天的证据看起来**跟它矛盾**(08-23 subglm 日志停在 11:49:09 再没长过,像是腿也死了;
08-19 四条腿却都活到跑完)⇒ 不许当既成事实,亲手探了两种杀法:

- **A `timeout 3`(SIGTERM 只打控制器)** ⇒ 腿活着跑完,控制器死在 `wait` 返回之前
  ⇒ **退出码永久丢失**,正是根因。
- **B `kill -TERM -<pgid>`(打整个进程组)** ⇒ 腿**照样**跑完(setsid 挪进新会话,组信号够不着)。

⇒ 前提**成立**。脚本与原始输出:`evidence/premise-probe-setsid-survival.md`。

**而且探针顺带告诉我方案里哪一半才是真正兜底的那半**:即使哪天腿也死了,
`plan` 因为写在**派发之前**,花名册照样答得出「派了谁」,只把那条腿标成未收尾(判据 R7)。
**记录的存活不依赖腿的存活** —— 这比我原来想的更强。

> 仍敞着:08-23 subglm 日志为什么没继续长,本探针没解释(可能它真死了,
> 也可能它活着但在等模型回话、正文最后才落盘)。**不阻塞本单。**

## ⚠️ 一处比我一开始估的绕的地方(如实记账)

腿有**两条**启动路径(`:522`~`:536`):

- `submimo|subkimi` → 直接 `setsid --wait "$cmd" ... &`
- `subdeepseek|subglm` → `run_leg ... &`,`run_leg` 内部**自己**又 `setsid --wait`,
  而且带**回落逻辑**(底座腿挂了 → 改派聊天腿,`:495` 那段)。

关键:`run_leg` 这个函数体跑在控制器的**后台子 shell** 里 ⇒ 和控制器同进程组 ⇒
**控制器被杀时它一起死**,只有它 setsid 出去的那个真腿活着。
所以 state 的写入点必须在**每一次 `setsid --wait` 的里面**,不能在 `run_leg` 里。
回落发生时会有两份 state,沿用既有的 `.agent.log` 命名习惯写成
`<prefix>.<leg>.agent.state` + `<prefix>.<leg>.state`。

我上一轮口头估"40~60 行"是**在读这段之前说的**,这里如实修正:主刀本身仍然不大,
但 `run_leg` 这条路让它比"改一个函数"要多碰两处。

## 测试策略(oracle,主 agent 亲自写,先红后绿)

判据文件:`tests/test-panel-roster.sh`(新),挂进既有的 `test-review-tooling.sh` 总跑。

**承重的两条**(其余是防回归):

- **R1 控制器被 SIGTERM 杀掉之后,花名册仍然算得出来且内容正确。**
  造一条假腿(sleep N 后按指定 rc 退出),派发后在**第一条腿交卷之前**杀控制器,
  等腿自己跑完,再跑 `panel-roster <prefix>` —— 必须出现正确的 rc。
  > 这一条直接复刻 08-23 的真实时间线。**它红着,才证明现在这个 bug 是真的。**
- **R2 state 由腿自己写,不是控制器写。**
  同上,杀控制器之后 `<prefix>.<leg>.state` 仍然会**在之后**出现。

**防回归**:
- R3 `plan` 必须在**任何一条腿交卷之前**就存在(不是跑完才写)。
- R4 花名册是纯函数:同样的盘上状态连算两次,**逐字节相同**。
- R5 **格式不许变**:正常路径下新实现算出的花名册,与旧实现的行格式逐字节一致
  (verify.md 里粘的那一行是下游,变了会静默污染所有历史对账)。
- R6 回落(agent→chat)时两份 state 各自归位,降级标记不丢。
- R7 `panel-roster` 对**残缺输入**要说人话:plan 在但某条腿没有 state ⇒
  必须印成"未收尾/KILLED",**不许印成 PASS,也不许整行消失**。

**红检**:每条断言至少一个变异(删写入点 / 把写入点挪回控制器 / 把缺失的 state
读成 PASS),证明判据咬得动。
