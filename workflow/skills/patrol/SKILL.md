# 每小时巡检

「谁来做」（谁巡检、谁答复执行方的提问、发现后归谁）见 `workflow/CLAUDE.md`「执行方提问与续接」的唯一定义。

**巡检每小时查哪些地方**（唯一定义，别处只写指向）：先做便宜检查：开着的 PR 和带派活标签的进行中 issue 上执行方是否有尚未答复的新问题；开着的 PR 当前 head 是否已有任务单要求的全部评审、是否已有该 head 的汇总（草稿状态的 PR 不催评审和汇总，见 `workflow/CLAUDE.md`「执行方提问与续接」）；普通 PR 当前 head 的合格 PASS 是否已达目标家数（未达时有没有待出结果的补派或交业主记录）；关卡当前检查摘要是否报告 PR 与 main 有冲突、不能干净同步；最近两小时合并的 PR 所 Closes 的 issue 是否仍开着；按 `post_merge_check` 设置应查的直接合并 PR 是否已有抽查标记；带派活标签的进行中 issue（标签从 `bin/_label_dispatch.py` 的 `LABELS` 读取，操作入口见 `docs/mac-host.md`）。没有开着的 PR 且没有进行中的派活 issue，也算需要处理。以上均无需处理时只回「无变化」，不读规则、不留言。

有事时先读 REVIEW-RULES.md，依 summary / delegate skill 处理：

- 执行方提问：按 `workflow/CLAUDE.md`「执行方提问与续接」处理。
- 评审齐全且未汇总：核实后在当前 head 发布 COMMENT 和 aiwork-summary 记录；照单修附完整修改单，先去掉旧派活标签再打修改类派活标签；合并或交业主时去掉派活标签。
- 目标家数未到的普通 PR：当前 head 没有待出结果的腿、也没有该 head 的汇总或交业主记录时，按 `summary` skill 补做汇总（含按策略用 `review-pr --auto` 补派）；已有腿在跑时不重复派。
- 合并后抽查：按 `post_merge_check` 设置核对已由关卡直接合并的 PR，见下节。
- 合并收尾：核实 PR 的 Closes 关联，手动关闭仍开着的对应 issue，并去掉派活标签。
- 关卡报冲突：按下节「冲突续接」处理。
- 空闲派活：按项目的有效决定和路线图写任务单进对应 issue，云端只核对 GitHub 上的任务内容和进展，再打任务类派活标签；云端读不到本机容量与占位，实际准入由[标签来源](../../../bin/_label_dispatch.py)判断，多打的标签由标签来源排队；写单前按 `workflow/skills/delegate/SKILL.md`「按内容分开派单」核对。拿不准交业主。

路线图记录方式见 REVIEW-RULES.md 第二节「待办与业主决定」。谁的话算指令见 `workflow/CLAUDE.md`「执行方提问与续接」的唯一定义。不自行批准、贴合并标签、推代码或修改关卡。

需要业主批准具体 PR 的具体提交、添加项目关卡策略指定的合并标签 或拍板时，用运行环境配置的通知入口推送一句大白话，写清要做什么；不需要业主做事时不推送。

## 合并后抽查

本节是合并后抽查的唯一定义；比例设置见项目 `.aiwork/policy.json` 的 `post_merge_check`，关卡校验格式。

抽查对象是**由关卡直接合并的 PR**（合并者是策略指定的关卡 App，且当前 head 的关卡摘要「实际合并路径」写明按目标家数直接合并；经合并标签合并的不在此列）。每轮巡检看最近 24 小时内合并、且还没有抽查标记的 PR。

比例：
- `mode` 为 `all`（未配置时也按 `all`）：每一单都查；
- `mode` 为 `sample`：PR 编号除以 `sample_every` 余 0 的查（`sample_every` 是正整数，例如 3 约等于每三单查一单）；
- `mode` 为 `off`：不查。

查什么（只读公开数据，不改代码）：
- 合入的是判过的 head：PR 的 head 提交就是关卡摘要判定并合并的那个提交；
- 该 head 上 CI 绿、关卡结论为放行，且没有未处理的 BLOCK 或 P1；
- 改动与 PR 说明、关联 issue 的范围一致，没有混进无关改动；
- 该 PR `Closes` 的 issue 已按本 skill「合并收尾」处理。

怎么记：
- 没发现问题：在 PR 上留一条评论，正文以「合并后抽查：已核对 <短提交号>，未发现问题」开头。这条评论就是「查过了」的标记，后续巡检看到标记不再查。
- 发现问题：先按 REVIEW-RULES 第二节第 1 条「待办与业主决定」记入项目待办，写清问题、证据和 PR/提交链接；再在 PR 上留标记评论，写明记到了哪个 issue。不重开 PR、不回滚、不自行修改 main；是否回滚或改方向由业主决定。

抽查只做核对和记录，不替代正式评审，也不改变关卡结论。

## 冲突续接

依据见 `workflow/skills/delegate/SKILL.md`「写单前」的冲突续接决定链接。本节是关卡报冲突后派单处理的唯一定义；关卡的自动同步行为见 `gate/README.md`「合并」。

整点巡检确认关卡当前检查摘要报告 PR 与 main 有冲突、不能干净同步时，直接给这单原来的执行方派「把最新 main 合进来、解冲突」的单，不用先问业主。按 `workflow/skills/delegate/SKILL.md` 写单，沿原关联 issue 派活；原执行方、原 PR 与分支以及续接方式按 `workflow/CLAUDE.md`「执行方提问与续接」核对。已有尚未完成的同一解冲突单时不重复派；同一 PR 的修改时机仍按 REVIEW-RULES 开头「一轮」及第四节「多个修改方并行」办理，不让两张单同时修改该 PR。无法核实原执行方或关联时，按「执行方提问与续接」的分工处理，不猜身份另开 PR。

解完按 `workflow/CLAUDE.md`「一个任务的走法」检查、推送同一分支，等当前 head 的 CI 通过后交接并自动派评审。手工解冲突不沿用原评审，重新评审；从严档和判卷面的单最后仍由业主批准。不另造派活或评审流程。
