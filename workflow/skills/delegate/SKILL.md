# delegate — PR 任务单

评审与修复规则见 [REVIEW-RULES.md](https://github.com/SunJ1ayu/aiwork/blob/main/REVIEW-RULES.md)，项目已接受风险见项目 main 的
`.aiwork/accepted-risks.md`，正式评审与合并条件见项目关卡策略。
任务的 PR 走法见 `workflow/CLAUDE.md`；这里只提供派 PR 任务的任务单格式。

## PR 任务单

把一整个 PR 任务派给另一个 agent 时用这个格式。对方按 `workflow/CLAUDE.md`「一个任务的走法」自己写测试、开 PR。
对方可能断线或换了一个，没有之前的上下文，所以任务单要自己就能看懂；一张任务单只管一个 PR；给同一个对方一次只派一张。

开头一段写：哪个仓库；从最新 main 拉新分支，还是接着改哪个 PR 的哪个分支；在对方自己的工作树里改。修评审时写明第几轮、评审在哪里看。

写单的一方：改规矩或文档的任务单，动笔前先按 REVIEW-RULES 第一节「同类一起扫」查清这个概念在哪些地方出现，不只改眼前那一句。

- 【开工前】对方先读任务单和它点到的代码、规矩，列出含糊、冲突、和现有规矩对不上的地方；有就先停下问，没有再动手。
- 【目标】现在是什么样、哪里不对。只写问题，不写改法。
- 【已定的决定】已经定下、对方不用再选的：改在哪一处，哪些要删。几处都要做的事，写明放在哪一处、各处调用。只定行为和位置，不定代码形状：「现有测试原样通过」这类要求会逼对方多包一层（PR #22）。写要求，不写手段。要写清要的效果和边界（例：「同时打开的句柄数是固定的小数，不随深度增长」），不要只写一种做法（「遍历不靠递归」只说了手段，换一种写法又撞上同类问题，PR #49）。会推翻旧测试或旧说明的，写明可以替换（PR #50）。
- 同一件事出现在多处的，按 REVIEW-RULES 第一节「同类一起扫」写清搜什么、在哪些范围里搜，不列行号；对方在 PR 里列出全部命中和各自的处理（PR #42 连续两轮因为手列行号漏改）。
- 【完成标准】改代码时要补哪些测试（先红，怎么算见 REVIEW-RULES 第一节第 3 条第 1 步）；全跑测试，推到哪个分支、等 CI 绿；用 `review-pr` 跑哪几家评审；PR 说明里要有各腿结果表，失败的写原因；然后停下，等汇总（见 `summary` skill）。汇总出来以前推不推，见 REVIEW-RULES 第四节「多个修改方并行」第 5 条。只改文档的，不要求加永久测试；一次性的检查见 `workflow/CLAUDE.md`「做事的方法」。
- 【不做什么】这次不动的，比如评审里不拦的 P2、P3，关卡，代码里的旧注释。
- 【前提不成立时】哪种情况说明任务单的前提错了；遇到时停下来说明，不要另写一套绕过去。
