# delegate — PR 任务单

评审与修复规则见 [REVIEW-RULES.md](https://github.com/SunJ1ayu/aiwork/blob/main/REVIEW-RULES.md)，项目已接受风险见项目 main 的
`.aiwork/accepted-risks.md`，正式评审与合并条件见项目关卡策略。
任务的 PR 走法见 `workflow/CLAUDE.md`；派单规则和任务单格式在这里定义。

## 写单前

任务单只写「做什么」，不写「怎么做」，靠评审纠正。单子写得像施工图，会让执行方和评审都沿着写单方的思路错；接受有时多一轮返工的代价。

业主要拍板的选择题，先用一条消息单独问业主，不写进任务单。碰到岔路，写单前先用 `explore` 让几条腿各提一个方案，整理成给业主的一道选择题，业主定了再写单。岔路指两条以上都说得通、代价不同、选错了要返工不止一轮的选择；是不是岔路，由写单方判断。工具用法见 `workflow/skills/explore/SKILL.md`。

没有固定的预审步骤。单子里写成事实的那几句，写单方自己核过；写「不改某个文件」前，先核实这次改动会不会让它失效。
不写行号级指导、挂在哪一行、字段名、建议实现，不写【建议做法】、自查表，也不列「写单方查过」或「汇总方查过」的清单。
执行方自己读代码，自己按 REVIEW-RULES 第一节「同类一起扫」查找和处理同类问题。
汇总核对清单见 `workflow/skills/summary/SKILL.md`「汇总核对清单」。

## PR 任务单

把一整个 PR 任务派给另一个 agent 时用这个格式。对方按 `workflow/CLAUDE.md`「一个任务的走法」自己写测试、开 PR。
对方可能断线或换了一个，没有之前的上下文，所以任务单要自己就能看懂；一张任务单只管一个 PR；给同一个对方一次只派一张。

开头一段写：哪个仓库；从最新 main 拉新分支，还是接着改哪个 PR 的哪个分支；在对方自己的工作树里改。修评审时写明第几轮、评审在哪里看。

- 【开工前】执行方先读任务单、代码和规矩；只有要求做不到或互相冲突才停下说明，其余由执行方自己判断并开工。
- 【目标】现在是什么样、哪里不对。只写问题，不写改法。
- 【业主已定的边界】业主已定的行为、效果和限制，以及为什么这样定；不替执行方定实现位置或做法。
- 【完成标准】改代码时要补哪些测试（先红，怎么算见 REVIEW-RULES 第一节第 3 条第 1 步）；全跑测试，哪些验证要真实运行，推到哪个分支、等 CI 绿；用 `review-pr` 跑哪几家评审；PR 说明里要有各腿结果表，失败的写原因；然后停下，等汇总（见 `summary` skill）。汇总出来以前推不推，见 REVIEW-RULES 第四节「多个修改方并行」第 5 条。只改文档的，不要求加永久测试；一次性的检查见 `workflow/CLAUDE.md`「做事的方法」。
- 【不做什么】这次不动的，比如评审里不拦的 P2、P3，关卡，代码里的旧注释。
- 【前提不成立时】哪种情况说明任务单的前提错了；遇到时停下来说明，不要另写一套绕过去。
