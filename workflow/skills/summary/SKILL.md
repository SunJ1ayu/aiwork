# summary — 一轮评审的汇总

评审与修复规则见 [REVIEW-RULES.md](https://github.com/SunJ1ayu/aiwork/blob/main/REVIEW-RULES.md)，项目已接受风险见项目 main 的
`.aiwork/accepted-risks.md`，放行条件见项目关卡策略。这里只说汇总这一步怎么做。

汇总是流程里固定的一步，不是谁的习惯：现在由主评审做，以后由 OpenClaw 叫醒一个能读代码、跑测试的强模型来做，做法都按这份。

## 什么时候做

当前 head 上，`review-pr` 派出的各条腿都有了结果：给出结论，或者明确失败（额度、超时）。各条腿只审当前这一版；跨轮次、跨各家的判断都在这一步做。

## 读什么

- 当前 head 上各家的评审，以及失败的腿和原因；
- 这个 PR 前几轮的汇总（发在 PR 上），轮数从这里数；
- PR 说明里修改方逐条写的处理；
- 业主在 issue 和 PR 里写下的决定。只在对话里说过、没写下来的，不算。

## 怎么做

1. 去重：同一处问题合成一条，注明哪几家提的。
2. 核实：在断网的隔离副本里跑全套测试；每条 P1 照描述复现。算不算 P1、复现不了还说不清时怎么办，见 REVIEW-RULES 第二节和第四节，这里不另定。抽查新测试在修之前的代码上是红的；要真机才能确认的，标成待业主确认。
3. 定级：按 REVIEW-RULES 第二节，分清本 PR 新引入的和原来就有的。
4. 决定下一步，只有四种：
   - 没有 P1：PASS。P2 写进汇总，合并后记进对应的 issue。
   - 有 P1，轮数没到 REVIEW-RULES 第三节的上限：BLOCK，用 delegate 的「PR 任务单」写下一张修改单。反正要重跑评审时，顺手的小 P2 可以放进同一张单。
   - 同一类问题连续两轮：换思路（REVIEW-RULES 第三节）。写清前提错在哪、新做法是什么，连同任务单草稿交业主；业主批准后再派。
   - 交业主：到了轮数上限还有 P1；严重程度说不清；结论取决于业主没写下来的意图；要改判卷面。写清每轮找到几条、是不是在收敛、剩下什么，以及建议。见 REVIEW-RULES 第三节。
5. 发到 PR 上：一条评审，事件用 COMMENT。汇总不批准、不贴合并标签、不推代码。

## 汇总的格式

- 标题：独立审核 · head <短提交号> · 第 N 轮
- 这一轮做对了什么；核实了什么（跑了什么、结果如何）；各家结果（谁 PASS、谁 BLOCK、谁失败及原因）；
- 每条 P1：在哪、怎么触发、实际得到什么、应该得到什么、哪家提的、要求怎么改（只写要求和位置，不写代码形状）；
- P2、P3；
- 刹车：这是第几轮；
- 「评审的处理」表：来源 | 处理；
- 最后一行：Conclusion: PASS 或 Conclusion: BLOCK。
