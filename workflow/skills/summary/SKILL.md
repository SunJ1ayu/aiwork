# summary — 一轮评审的汇总

评审与修复规则见 [REVIEW-RULES.md](https://github.com/SunJ1ayu/aiwork/blob/main/REVIEW-RULES.md)，项目已接受风险见项目 main 的
`.aiwork/accepted-risks.md`，放行条件见项目关卡策略。这里只说汇总这一步怎么做。

汇总是流程里固定的一步，不是谁的习惯：现在由业主派的一个独立会话做，以后由 OpenClaw 叫醒一个能读代码、跑测试的强模型来做，做法都按这份。

## 什么时候做

什么时候汇总，见 REVIEW-RULES 开头「一轮」的定义。腿怎么审，见 REVIEW-RULES 第四节「多条评审腿审同一个 PR」第 1 条；跨轮次、跨各家的判断都在汇总这一步做。

## 读什么

- 当前 head 上各家的评审；
- 派腿一方写在 PR 说明里的各腿结果表，失败的腿和原因从这里读；
- 这个 PR 前几次汇总（发在 PR 上）；
- PR 说明里修改方逐条写的处理；
- 业主在 issue 和 PR 里写下的决定，只读写下来的。结论取决于业主没写下来的意图时，见 REVIEW-RULES 第三节第 1 条。

## 怎么做

1. 去重：同一处问题合成一条，注明哪几家提的。
2. 核实：在断网的隔离副本里跑全套测试；每条 P1 照描述复现。算不算 P1，见 REVIEW-RULES 第二节第 1 条；复现不了还说不清时，见第四节「多条评审腿审同一个 PR」第 3 条。抽查新测试在修之前的代码上是红的；要真机才能确认的，标成待业主确认。
3. 定级：见 REVIEW-RULES 第二节第 1 条。
4. 决定下一步：按 REVIEW-RULES 第三节第 5 条的优先顺序。选「合并」之前，先看关卡在当前 head 上的结论：除了业主批准还缺别的（比如额度不够、凑不齐几家不同家族的 PASS），就选交业主，写明缺什么。要派修改单时，用 delegate 的「PR 任务单」。P2 放不放进这张单，见 REVIEW-RULES 第三节第 4 条。
5. 发到 PR 上：用一个不是项目策略里 `reviewer_bot` 的账号发一条 COMMENT 评审（没有结论块的机器人评审，关卡会算成 BLOCK）。关卡不读汇总。汇总不批准、不贴合并标签、不推代码。
6. 下一步写「合并」或「交业主」的那次汇总，当场把这个 PR 历次汇总里还没记的 P2 都记进待办，每条注明这个 PR 的号；记在哪，见 REVIEW-RULES 第二节第 1 条。

## 汇总的格式

- 标题：独立审核 · head <短提交号> · 第 N 次汇总
- 这一次做对了什么；核实了什么（跑了什么、结果如何）；各家结果（谁 PASS、谁 BLOCK、谁失败及原因）；
- 每条 P1：要写的项见 REVIEW-RULES 第二节第 2 条，再补哪家提的、要求怎么改（怎么写要求，见 delegate 的【已定的决定】）；
- P2、P3；
- 刹车：已发几张修改单（怎么数见 REVIEW-RULES 开头「一轮」），到没到上限见第三节第 1 条；
- 「评审的处理」表：来源 | 处理；
- 结论行在前：写法见 REVIEW-RULES 第二节第 2 条。
- 下一步行在后：填 REVIEW-RULES 第三节第 5 条里的一档。
