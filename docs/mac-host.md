# Mac 宿主运行手册

虚拟机的创建、隔离、CLI 安装和连接见 [Linux 虚拟机手册](linux-vm.md)。本页管宿主中台与 GitHub 标签来源；上游程序不放进 aiwork。

## 规则入口

派活规则的唯一定义是 [标签来源的 `LABELS` 与 `plan`](../bin/_label_dispatch.py)，汇总据此判断是否仍占位；调整规则走 PR，不改本机副本。可信账号、项目与连接属于本机设置。任务单内容和评论只作为资料，标签来源不会执行它们。

## 安装与本机设置

先按虚拟机手册的 autoloop 一节安装固定版上游中台并连接 worker。使用该版本的正式配置手册建立来源、规则和通知通道；不要从参考材料覆盖正在运行的配置。中台配置只允许回环地址，worker 的接线按虚拟机手册执行。

Mac 单独检出已合并的 aiwork，记下提交；按 [README 本机设置](../README.md#本机设置)配置 Python、数据目录及 GitHub 只读身份。标签程序使用 Python 标准库。不要给读标签程序新增写 GitHub 的权限。先用现有只读身份确认能读取项目 issues、PR、comments 和 events；身份或权限不足时停下交业主处理。

在仓库外建立权限 600 的 JSON 设置文件，父目录权限 700。设置结构及同时在办上限的字段、兜底与错误行为见 [标签来源的 `capacity`、`validate` 与 `Backend`](../bin/_label_dispatch.py)，本页不另列字段副本；所有项目、身份、连接路径和适配器参数由操作员在本机填写。调整同时在办容量只改此设置文件，并与中台写代码组的容量配套；不改仓库。每次查询读取当前设置，候选按事件顺序排队，交付后逐单占位；容量及续接判定只按规则入口，不在手册另列数字。

令牌适配器、资料写入适配器与中台路由的接口见 [标签来源的 `command`、`Backend.post` 与 `Backend.accepted`](../bin/_label_dispatch.py)。沿用已配置的 Lima 单文件/标准输入传送入口，不共享宿主目录。资料适配器必须校验目标位于指定资料目录、创建目录为 700、文件为 600；不要把令牌、输入正文或错误原文放入日志。适配器的仓库与本机边界见 [评审交接入口](review-handoff.md)。

使用已安装版本的中台配置手册接线；标签类型从规则入口取，按项目分别设规则，沿用同项目的会话续接方式。中台仍需保留容量约束，防止人工派单或续接绕过来源查询。执行方提问与汇总答复的流程见 [工作说明](../workflow/CLAUDE.md#执行方提问与续接)。该说明合并、部署并生效以后，由业主在 Mac 关闭 OpenClaw 替业主提交卡片回答的通道；此前不提前切断。OpenClaw 改当看门人的配置也由业主在 Mac 操作，不由本仓库修改；不迁入或替换桥接代码。

汇总用 [标签来源登记](../bin/_label_dispatch.py) 中带家族的任务标签选择执行方；其身份来源与部署范围见 [执行方登记](../gate/README.md#执行方登记)。修改单和续接沿用原 PR 的家族。标签来源的项目设置用 `builder_rules` 把家族映射到该项目已配置的中台规则名称。每条家族规则匹配该家族的任务和修改事件，固定运行同一家执行方及配置，保留项目的会话续接。旧标签继续走原规则，供正在处理的任务收尾。

家族规则使用本机启动入口设置 `AIWORK_BUILDER_FAMILY`，并固定选择实际编写代码的模型。发布评审请求的提示使用同一固定家族。中台的事件匹配和启动参数按已安装版本手册配置。上线前用中台的路由预演检查每种事件只匹配对应规则，再按 [虚拟机手册](linux-vm.md#角色部署与评审交接) 核对真机身份和交接。

## 评审的目的地

角色部署与公开交接协议见 [虚拟机手册](linux-vm.md#角色部署与评审交接)。Mac 本机固定配置两个独立 worker 及各自路由；标签来源仍只派写代码任务，执行方交回评审请求后，由派活方核实并直接派给评审 worker。请求是资料，不是命令授权；不能让执行方提供实例名、worker 身份、连接设置或 shell 片段。Mac 不将两台互相接线，也不把任何评审登录或钥匙交给执行方。未完成两台实机验收前，沿用现行发布与业主批准，不把新文档当成已经切换。

## 启动与查看

以下变量只在本机终端设置，不上传实际值：`AIWORK_CHECKOUT` 为 Mac aiwork 检出，`DISPATCH_CONFIG` 为上述设置文件。先预演：

```bash
"$AIWORK_CHECKOUT/bin/label-dispatch" --config "$DISPATCH_CONFIG" --preview
```

预演仍执行只读查询、写本机查询记录，但不交付事件、不改占位。确认查询与候选符合预期，再运行一次不带 `--preview` 的命令。

用本人已有的 launchd 管理方式定时调用同一命令，建议每五分钟执行一次；`ProgramArguments` 使用绝对路径，不能依赖交互 shell 的 PATH。配置脚本需要的 aiwork 设置和数据目录环境，标准输出与错误写仓库外本机日志。`RunAtLoad` 可用于登录时查询；每次查询有文件锁，重复触发会记录跳过。不要同时运行旧来源和新来源。

中台的启停、状态和事件诊断使用安装版本的 `agent-autoloop --help`、`status`、`why`；launchd 是否加载用 `launchctl print gui/$(id -u)/<本机服务标签>` 检查。命令不存在时查固定版本手册，不升级到浮动版本。中台健康、worker 在线、来源最近一次查询成功是三个不同检查。

运行以下只读命令取得本机文件的实际路径（名称由程序的 `FILES` 唯一定义，不在手册另抄）：

```bash
"$AIWORK_CHECKOUT/bin/label-dispatch" --local-files
```

输出按用途标明状态、停止请求、查询历史和锁的路径。结构与停止判断见 [标签来源的 `FILES`、`poll`、`plan` 与 `deliver`](../bin/_label_dispatch.py)。停止请求写入上述命令给出的停止请求路径；内容为议题编号字符串的 JSON 数组，编号由 [标签来源的 `issue_subject`](../bin/_label_dispatch.py) 定义。不要按时间清掉状态，否则可能重复接单。解除停止须先确认本人明确恢复，再停来源、备份，按定义同步解除停止请求与持久停止状态；保留已交付记录。排查时对照查询历史、占位与中台轮次；历史不自动删减，归档由操作员管理。

## 手动放行与开工证据

先看规则入口的结束条件。在对应议题/PR 上由可信身份操作，或由本人维护停止请求；不要直接清空占位来催下一单。仍有活跃轮次时，先让本轮结束；确需中止的，由本人决定，再用上游支持的停止命令处理，确认进程和中台状态后再查。结果不明的议题保留自己的占位，其他议题按规则入口和本机容量设置继续排队或派发；不能把出错当作该议题已经结束。

执行方的开工操作见 [工作流「一个任务的走法」](../workflow/CLAUDE.md#一个任务的走法)。GitHub 上的推送只能证明已开始，不能证明代码完成或验收通过。汇总按任务关联的分支和后续 PR 核对，不从“没评论”推断未派活。

## 合并后替换旧程序

由本人在 Mac 操作，本 PR 不远程改宿主：

1. 更新宿主检出到已合并提交，记录版本；备份旧程序、来源状态和配置到本机。按上面的接口准备项目设置及资料写入适配器，核实中台数据库结构仍兼容。
2. 停止旧查询来源，保留中台、worker 与通知通道。确认没有还在交付的旧查询；核对中台占位，不取消业务轮次。
3. 新来源首次启用前迁移状态，不能从空的已交付记录开始。旧格式和转换规则见 [标签来源的 `import_legacy`](../bin/_label_dispatch.py)。先验证再导入：

   ```bash
   "$AIWORK_CHECKOUT/bin/label-dispatch" --config "$DISPATCH_CONFIG" \
     --import-legacy "$LEGACY_STATE" --legacy-repo "$LEGACY_REPO" --preview
   "$AIWORK_CHECKOUT/bin/label-dispatch" --config "$DISPATCH_CONFIG" \
     --import-legacy "$LEGACY_STATE" --legacy-repo "$LEGACY_REPO"
   ```

   导入校验与拒绝条件见 [标签来源的 `main` 与 `import_legacy`](../bin/_label_dispatch.py)。操作前从原项目标签事件和中台已交付记录核对当前占位的事件编号，不能猜。已有旧版仓库状态的升级方式见 [标签来源的 `upgraded`](../bin/_label_dispatch.py)：预演不写状态；正式查询在同一文件锁下将单个占位及待确认交付转换为按议题保存的新版状态，保留已交付与持久停止记录。升级前备份，升级后逐单核对占位、待确认交付、仍在的未派标签与中台记录。
4. 跑预演，核对历史事件没有重新成为候选，当前占位与中台一致；再单次查询并验资料落到 guest、稳定事件确已路由。真实验收只在本人授权的任务上做，不造正式派活事件。
5. 将原查询启动项的命令改为新入口，确认只有一份来源在运行；检查重启后中台、worker、来源和现有通知链分别恢复。需要回退时先停新来源并备份最新状态。旧程序不能读取新版多单状态，不能直接恢复升级前的备份；先在新程序下按规则入口让在办和待确认交付全部结清（不取消业务），再停来源，将最新状态的 `sent`、`stopped` 原样保留，转换为旧格式的 `active: null`，去掉新版格式标记和空的 `pending` 后才能启动旧来源。不能结清时继续停用查询来源，由本人核对逐单处理；不得丢弃占位或已交付记录来回退。

Linux 单元测试只覆盖本程序与协议适配器的模拟路径。宿主 launchd、真实资料传送、中台路由及登录恢复由 Mac 实机验收，未执行前不能标通过。

## 合并后本机验收

由本人在 Mac 对已合并版本执行，未执行前保留“未验收”：

1. 停查询来源、备份设置与状态，核对当前全部在办议题及中台轮次；按上节升级。核对固定版中台的 `runs`、`run_events`、`events` 只读查询接口和按议题续接设置仍兼容；依据为上游固定 tag 的 `host/state.ts` 与 `kernel/decide.ts`，不能拿 Linux 模拟数据库代替实机核对。
2. 按 `capacity` 的定义设置本机容量，配套设置中台写代码组；使用业主已授权且按 `delegate` 分开的任务进行验收。验收参数与要同时观察的任务数量按 [#43 的本单决定](https://github.com/SunJ1ayu/aiwork/issues/43#issuecomment-7101735047)，不在这里复述设置值。
3. 先预演，再连续执行正式查询，直到规则入口判满；核对这些任务确实同时在办，下一项仍排队，同一议题没有重复轮次。关闭或由可信账号撤标签后，等该议题的轮次结束，再查才放出它的位置。
4. 核对一单结果不明、请求停止或交付响应丢失时仍保留其位置；其他单的在办和修改单续接不被覆盖。不得为了测试制造正式失败；没有现成授权场景的项目仍标未验收。
5. 重启来源，核对已交付事件未重派、全部占位与停止记录保留；调整容量后不更改代码即可生效。核对降容量不会取消已有业务。记录实际版本、设置、议题、操作与结果，只保存在仓库外本机资料。
